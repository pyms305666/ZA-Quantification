# 练习12 参考答案（发布演练——以本项目真实发布 V1.1.1 为例）

> 发布工程没有"标准答案"，但有**标准流程**。下面是本项目真实执行 V1.1.1 发布的
> 完整复盘（含踩过的坑），对照你的演练记录打分。

## 第 1 步：改版本号 ✅

- `VERSION` 文件：内容就是版本号（单一事实来源，打包时嵌进 exe，启动时读出显示）；
- 同步改 `static/index.html` 的品牌版本号和 `?v=` 参数（否则浏览器缓存旧前端——
  "改了代码页面没变化"的头号原因）。

## 第 2 步：打包 ✅

```powershell
pyinstaller --noconfirm --clean --onefile --name "ZA量化-XX版" --icon assets/icon.ico `
  --add-data "static;static" --add-data "config.json.example;." --add-data "VERSION;." launcher.py
```
- exe 名字**必须带路线标记**（AB协程版 / C直连版）——用户要知道自己下载的是哪条路线；
- 打包前确认在**正确的分支**上（两条路线的代码不同，打错分支=发错版本）。

## 第 3 步：冒烟测试（5 项）✅

1. 双击 exe → 天勤连接成功；
2. 页面正常（K线/盘口/决策有数据）；
3. `/api/v1/status` 的 `route` 是当前路线；
4. 关闭后无残留 python 进程；
5. exe 文件名带路线标记。

## 第 4 步：提交 ✅

- `git add` 前先 `git status` 检查：**config.json 和 .tqsdk/ 绝不能出现**（密码卫生）；
- 提交信息带路线标记：`【C路线】v1.2.2-c-diff: ...`——历史里能一眼看出哪条路线的提交。

## 第 5 步：标签与 Release ✅（真实踩坑记录）

```
git push -u origin master route-ab route-c     # 推分支
git tag -a V1.1.1 <主线提交> && git push origin V1.1.1
```
踩过的坑：
1. **大小写标签冲突**：Windows 文件系统不分大小写，本地已有 `v1.1.1`（小写）时
   `V1.1.1` 建不出来——先删旧标签（`git tag -d` + `git push origin :refs/tags/v1.1.1`）；
2. **中文文件名**：GitHub 会清洗资产的中文名（"ZA量化"→"ZA."）——
   资产用 ASCII 名（`ZAQuant-V1.1.1-C-Direct-Setup.exe`），说明里写清对应关系；
3. Release 说明里放 **SHA-256 校验和**：下载者可验证文件完整性。

## 第 6 步：复盘（示例）

**印象最深**：创建 Release 的 JSON 请求——body 里有大段中文和反引号，
直接在命令行拼字符串两次都"Problems parsing JSON"；
最后用 Python 读文件生成 payload.json 再 `curl -d @payload.json` 才成功。
**教训**：复杂参数先落成文件，不要在命令行里手拼。

**遇到的问题与解决**：Git Bash 会把 `/VERYSILENT` 这类参数误转换成路径
（MSYS 路径转换），导致安装包的静默验证一直失败——
加 `MSYS_NO_PATHCONV=1` 解决。这类"工具链的坑"只能靠遇到一次记一次。

## 自评标准

- 6 步全部独立完成、冒烟 5 项全过 → 毕业合格 🎓
- 出现"提交了 config.json" → 回炉第 4 步（这是红线）
- 出现"exe 名字没有路线标记" → 回炉第 1 步（用户分不清版本就是发布事故）
