## 〇、前置实测：天勤合约服务器的行为（2026-09-18 实测）

这些事实直接决定 ③ 的设计，接手后不要再假设，直接引用本节：

| 探测 | 结果 |
|---|---|
| `HEAD` 请求 | **405 Method Not Allowed**（只允许 GET/OPTIONS，无法用 HEAD 预检） |
| `GET` + `Accept-Encoding: gzip`（全量） | `Content-Encoding: gzip` + `Transfer-Encoding: chunked`（无 Content-Length），压缩流约 8~11MB |
| `GET` + `Range: bytes=0-1023`（+ gzip 头） | **`206 Partial Content`，且返回的是未压缩字节**（`Content-Range: bytes 0-1023/354745357`，无 `Content-Encoding`） |
| 相同 Range 请求两次 | 字节逐位一致 |
| 服务器暴露的辅助头 | `Etag`、`Accept-Ranges: bytes`、`Content-Range`（均在 `Access-Control-Expose-Headers` 中） |

**结论**：
1. 断点续传**只能基于 identity（未压缩）表示**做 Range——服务器对 Range 请求不走 gzip。
   identity 全量 354MB，按交接文件实测的 ~0.5MB/s 限速约需 **12 分钟**。
2. 必须用 **`If-Range: <ETag>`** 防止目录文件在续传期间更新导致字节错位
   （If-Range 不匹配时服务器返回 200 全量，正好等于"从头重下"，语义安全）。
3. 请求续传时显式发 `Accept-Encoding: identity`，钉死表示，防止服务器行为变化。

## 二、Android release 签名与发布流程

**现状**：`mobile-app/app/build.gradle` 的 release buildType 仍
`signingConfig signingConfigs.debug`（第 27 行），即发布包 = debug 签名。

### 2.1 步骤

1. **生成 keystore**（一次性，妥善离线备份密码；keystore 本身不进仓库）：
   ```bash
   keytool -genkeypair -v -keystore zaquant-release.keystore -alias zaquant \
     -keyalg RSA -keysize 2048 -validity 10950
   ```
2. **签名配置**：新建 `mobile-app/keystore.properties`（加入 `.gitignore`）：
   ```properties
   storeFile=E:/keys/zaquant-release.keystore
   storePassword=***
   keyAlias=zaquant
   keyPassword=***
   ```
   `build.gradle` 增加：
   ```gradle
   def keystoreProps = new Properties()
   def ksFile = rootProject.file("keystore.properties")
   if (ksFile.exists()) keystoreProps.load(new FileInputStream(ksFile))
   android {
       signingConfigs {
           release {
               storeFile file(keystoreProps["storeFile"])
               storePassword keystoreProps["storePassword"]
               keyAlias keystoreProps["keyAlias"]
               keyPassword keystoreProps["keyPassword"]
           }
       }
       buildTypes {
           release {
               signingConfig signingConfigs.release   // 替换现有 debug 行
           }
       }
   }
   ```
   （properties 不存在时保持 debug 签名，保证他人 clone 后仍可出 debug 包。）
3. **构建与验证**：
   ```bash
   cd mobile-app && ./gradlew.bat --no-daemon assembleRelease
   # 验签
   %ANDROID_SDK%/build-tools/34.0.0/apksigner.bat verify --print-certs dist/xxx.apk
   # 记录 SHA-256
   certutil -hashfile dist/xxx.apk SHA256
   ```
4. **版本号联动**（下次发版 v1.1.3）：`build.gradle`（versionCode 3 / versionName 1.1.3）、
   `electron/package.json`、Inno Setup 脚本、手机"关于"页，四处同步。

### 2.2 风险提示（必须告知用户）

- **签名变更 = 不能覆盖安装**：真机上已装的 debug 包必须先卸载才能装 release 包，
  卸载会清掉 App 数据（登录凭据、自选列表）。测试分发期可接受；一旦用 release 签名发出
  第一版，此后必须永远用同一 keystore 签名升级。
- minify 保持 `false` 不动：Chaquopy 的 Python 反射与 Java 桥接在混淆下风险高，
  当前无混淆需求。

### 2.3 验收标准

- `assembleRelease` 产物 `apksigner verify` 通过，证书指纹留档。
- `keystore.properties` 与 keystore 均不在 git 跟踪中（`git status` 干净）。
- debug 构建路径不受影响（clone 后直接 assembleDebug 仍成功）。

## 三、合约目录断点续传（两端 `tqdiff/auth.py`，需镜像同步）

**现状**（`tqdiff/auth.py::download_symbol_file`）：gzip 全量一次流写 `.gz.tmp`，
`finally` 中 `tmp.unlink()`——任何中途失败都从 0 重下（"4MB 归零"的遗留根因）。

### 3.1 设计（基于 §〇 实测事实）

双路径策略，现有 gzip 快路径保留为首选：

```
┌─ 路径 A（首选，现状）：全量 GET + gzip，8~11MB ≈ 17 秒
│    成功 → 落盘 .gz → ijson 解析 → pickle 索引（现状逻辑，不动）
│    中途失败 → 进路径 B
│
└─ 路径 B（新增，续传）：identity + Range 续传
     状态文件：<cache>/latest.json.part + <cache>/latest.json.part.etag
     ① 已有 .part（大小 N，ETag E）→
          GET Range: bytes=N- / If-Range: E / Accept-Encoding: identity
          ├─ 206 → 追加写入 .part，完成后 .part → latest.json
          ├─ 200 → ETag 已变（目录更新）→ 丢弃 .part 从 0 收
          └─ 416 → .part 比服务器文件大（异常）→ 丢弃重收
     ② 无 .part → 全量 identity 下载（带 ETag 逐块落盘）
     完成后：ijson 直接解析 latest.json（新增 index_from_json_file，
             不经 gzip）→ save_index → 删除 latest.json（只留 25MB pickle）
```

实现要点：

- `Etag` 从响应头取，逐块更新 `.part.etag`（首块写入后不再变）；
- 写入用 `rb+` append 语义，崩溃安全（bytes 落定即可续）；
- `finally` 只对 gzip 快路径的 `.gz.tmp` unlink；`.part` 永不主动删（除 200/416 重置）；
- 超时参数维持 `(15, 120)`（0.5MB/s 下 256KB 块 0.5s/块，读超时安全余量足够）；
- `symbol_index.py` 增加 `index_from_json_file(path, progress)`（ijson 直接吃明文 JSON，
  复用现有 `parse_instrument_record` 管道）。

### 3.2 同步与测试

- 改根目录 `tqdiff/auth.py` + `tqdiff/symbol_index.py` 后，**逐字节镜像**到
  `mobile-app/app/src/main/python/tqdiff/`，跑 `python tools/check_core_drift.py --strict`；
- `tests/` 新增用例（monkeypatch `requests.get` 模拟服务器）：
  1. `test_resume_continues_from_206`：预置 .part + etag → 206 → 文件完整、只补了尾部；
  2. `test_resume_restarts_on_etag_change`：If-Range 不匹配返回 200 → .part 重置；
  3. `test_resume_on_416_resets`；
  4. `test_gzip_path_unchanged`：无 .part 时仍走 gzip 快路径；
  5. `test_index_from_json_file`：明文 JSON 解析与 gzip 路径产出一致。
- 真实验收（交易时段或任意时段，该文件与行情无关）：
  下载中途 `Ctrl+C` / 断网 → 重启 App → 日志显示 `resume from N bytes (N>0)` →
  最终目录就绪；证据回填 `docs/验证记录/`。

### 3.3 验收标准

- 上述 5 个单测通过，全套 `python -m unittest discover -s tests` 通过（≥64）；
- `check_core_drift.py --strict` 漂移 0；
- 真机模拟中断至少 2 次，续传推进、最终索引可用，二次打开秒开。

## 四、凭据安全存储

**现状**：两端 `config.py` 把账号密码明文存
`credentials.json`（桌面 `.tqsdk/`、手机 App 私有目录），环境变量 `TQ_PASSWORD` 已支持。

### 4.1 桌面端：Windows 凭据管理器（本次做）

- 引入 `keyring`（Windows 后端为 wincred，纯 ctypes，无原生编译，PyInstaller 打包无碍）；
- `config.py` 读取顺序改为：**环境变量 → 凭据管理器 → 明文文件（遗留兼容）**；
- 保存时：写凭据管理器，并**删除明文文件**（或仅保留账号不含密码，便于登录页回显）；
- 首次从明文迁移：读到明文文件 → 写入凭据管理器 → 删除明文；
- `requirements.txt` 加 `keyring==25.x`；打 C 直连版 exe 后烟测登录一次。

### 4.2 手机端：维持现状 + 说明（本次不做 Keystore，留档理由）

- Android 的 `credentials.json` 位于 App 私有沙箱（`za.filesdir`），
  系统级已隔离其他应用，明文风险远低于桌面用户目录；
- Android Keystore + AES-GCM 加密需经 Java 桥接（Chaquopy 调 Java 可行但要动
  `BackendService`/`config.py` 两侧），收益/成本比低，**列为可选后续**；
- 验收改为确认性检查：`adb run-as com.zaquant.mobile ls files/.tqsdk/` 确认
  文件仅在私有目录（debug 包可查；release 包不可 run-as，改为文档说明）。

### 4.3 通用红线

- `config.json`、`credentials.json`、`keystore.properties`、`*.keystore`
  均在 `.gitignore`，提交前 `git status` 核对；
- 凭据只经环境变量 / 系统存储，不进日志（现有代码无打印，保持）。

### 4.4 验收标准

- 桌面：登录一次后 `.tqsdk/credentials.json` 不含密码（或不存在），
  凭据管理器可查到条目；重启进程免登录仍有效；
- 明文遗留用户升级后自动迁移，无感；
- 手机端行为不变（回归：登录、退出登录 `clear_credentials` 仍工作）。
