> 基于 2026-09-02 晚（夜盘时段）的实测。测试方法：单元测试 + curl 逐接口验证 + 内置浏览器
> GUI 黑盒测试（DOM 快照 + 截图），复现 3 轮完整"打开页面 → 拥塞 → 恢复"周期。
> 截图证据在 `gui-test-screenshots/`。
>
> v2：补充业界/开源项目经验（TqSdk 官方协程模式、vnpy 事件引擎教训、FastAPI 线程池机制、
> singleflight 模式、前端虚拟滚动与 ECharts 大数据优化），并据此升级修复方案。

## 二、三个"为什么"的直接答案

### 为什么 K 线总是被阻塞？

因为**页面一打开就触发一次"全量合约目录查询"，它把整个后端唯一的行情线程独占数分钟**。

时序如下（全部有实测数据支撑）：

```
浏览器打开页面
  ├─ app.js init() 同时发 4 个请求：status / instruments(无过滤) / kline / decision
  │
  ├─ instruments 无过滤 → 后端把 866 个合约分 18 批逐批查询天勤
  │     每批约 8 秒 → 总计约 2.5~4.5 分钟
  │     ★ 这期间 TqSdk 事件循环线程被独占，其他一切命令排队等待
  │
  ├─ kline 请求：前端 45 秒就放弃 → 显示"K线加载失败：HTTP 500"
  ├─ decision 请求：同样超时 → "评估不可用"
  ├─ WS 订阅：10 秒超时 → 失败 → 每 5 秒重试一次（继续加压）
  │
  └─ 更糟的恶性循环：
      前端每 6 秒轮询决策(4条K线命令)、每 15 秒轮询K线/状态
      每个超时请求占住一个 HTTP 线程池线程直到超时（决策接口最长 120 秒）
      → 40 个线程全部占满 → 连 /status 都不响应 → 整个服务活锁
```

**为什么永远好不了**：目录查询实测约 140~150 秒，而服务端给它限了 120 秒超时
（`tq/instruments.py:76` `run_command("get_instruments_info", missing, timeout=120.0)`）。
天勤的返回其实已经到了，但代码在 120 秒整抛出超时异常，**把已经完成的结果整个丢掉**，
`InstrumentManager._info_cache` 永远建立不起来 → 下次打开页面从头再来。实测 3 轮全部如此。

### 为什么切换合约时 K 线不切换？

`static/app.js` 的 `switchSymbol()`（411 行）逻辑是：改 `state.symbol` → 清空行情/决策 →
发 WS 订阅 → `await loadKline()`。问题在 `loadKline()`（339 行）失败路径：

- 拥塞窗口内该请求 45 秒超时，进入 catch，只把提示文字改成"K线加载失败"；
- **`state.kline` 里还是上一个合约的数据，`renderChart()` 不会被调用 → 图表保持旧合约的 K 线**；
- 首次加载还没数据时就是永久空白，直到某一轮 15 秒轮询赶上后端空闲才恢复。

另外还有一个竞态：`loadKline` 发请求时不带"请求序号"，快速连续切换合约时，
**旧合约的慢响应可能后到，把新合约的图表覆盖成旧合约的数据**（无任何防护）。

### 为什么切换周期（分时线）时 K 线也不切换？

周期按钮（432 行）只做两件事：改 `state.period` → 调 `loadKline()`。和切合约是
**同一条失败路径**：请求超时 → 图不变，但按钮已经高亮，看起来就是"点了没反应"。
（后端空闲时这条路径实测是好的：测试中点"日线"立即切换并完整渲染——见截图
`t2_daily_period.png`。所以"不切换"只在拥塞窗口内发生，而首次加载的拥塞窗口长达数分钟。）

## 三、根因定位（按贡献度排序）

### 问题 1（P0）：全量目录查询独占事件循环，且结果总被超时丢弃

- 触发点：`static/app.js:83` `loadInstruments()` 无 keyword/exchange 参数；
  `api/http.py:142` 不过滤；`tq/instruments.py:58` `list()` 把所有缺失合约一次性
  `run_command("get_instruments_info", ..., timeout=120)`。
- 执行点：`tq/client.py:310` `_get_instruments_info` 每批 50 个、18 批串行，
  每批一次天勤 graphql 往返（实测约 8 秒/批）。
- 架构约束：`tq/client.py` 的 TqApi 是**单线程事件循环**，所有命令 FIFO 队列串行——
  这本身是对的（TqSdk 非线程安全），但长命令没有任何"让出/分片"机制。

### 问题 2（P0）：命令队列"超时不取消"，前端轮询把拥塞放大成活锁

- `tq/client.py:143` `run_command` 超时只是等待方放弃，**命令仍会执行**，
  结果 set 给没人等的 future 后被丢弃——队列里堆的全是"执行了也白执行"的命令。
- 前端轮询（`app.js:465`：决策 6s×4 命令、K线 15s、状态 15s）+ WS 订阅重试 5s
  （`app.js:390`）在拥塞期持续入队。
- 每个 sync 端点占住线程池线程直到超时（决策 = 4×30s），anyio 默认 40 线程
  耗尽后**整个 HTTP 服务无响应**（实测 `/status` 挂起 10 分钟以上）。
- 连锁反应：连续命令超时触发 `tq/client.py:161` 的强制重连，重连后 8 秒预热期
  又让所有请求快速失败一轮，进一步加剧前端重试。

### 问题 3（P1）：前端加载失败时图表状态管理缺失

- `loadKline` 失败不清空旧数据、成功不清除错误提示（"K线加载失败"文字永久残留，
  即使图已渲染好——见截图）；
- 切换合约/周期无加载态、无请求竞态防护；
- 合约列表初始请求失败后**永不自动重试**（只有输入搜索或点交易所标签才触发），
  所以拥塞过后列表仍是空的。

### 问题 4（P1）：错误语义失真

- 目录缓存未命中 + 拥塞期查询失败，会被 `InstrumentManager.get` 当作"合约不存在"，
  决策接口返回 422 "合约不存在：SHFE.rb2610"（实测截图）——其实是"目录还没就绪"。
- `TqClientError` 在 kline/instruments 端点未捕获 → HTTP 500 + 整页 traceback，
  应映射为 503 + 结构化错误。

## 四、其他发现（顺手记录）

5. **量仓因子评分永不触发**：`market/evaluator.py:230` 读 `quote.get("pre_open_interest")`
   和 `quote.get("direction")`，但 `MarketQuote.to_dict()`（`market/model.py:50`）不输出
   这两个字段 → `oi_delta` 恒为 0，最多 10 分的增仓/减仓评分是死代码；前端"日增仓"恒显示 +0。
6. **真实账号密码已提交进 git**：`.gitignore` 写了排除 `config.json`，但该文件已被跟踪。
7. **最新价虚线标签被右边缘裁剪**（截图 t2 可见"308…"只显示一半）。
8. **后端进程两次无征兆消失**：日志无崩溃痕迹，均发生在长时间高负载后，原因未查明；

## 五、修复方案（v2，按业界经验升级）

### 0. 路线选择：三条路，推荐 A+B 组合

| 路线 | 内容 | 评价 |
|------|------|------|
| **A. 最小修复** | 前端不拉全量目录 + 后端查询"提交后立即返回、后台完成写缓存" | 1~2 天，风险最低，先止血 |
| **B. 官方协程化** | 用 TqSdk 3.8+ 原生协程（`api.create_task` / `await`）重构慢查询 | 与官方推荐一致，彻底消灭"长命令堵循环" |
| C. 换协议层 | 绕开 TqApi，直接实现天勤 DIFF websocket 协议（参考 [tqsdk-go](https://github.com/pseudocodes/tqsdk-go)、[tqsdk-rs](https://github.com/pseudocodes/tqsdk-rs)） | 重写成本高，仅在未来多语言/大规模时考虑 |

vnpy 社区的实战教训验证了我们的诊断：**单线程事件消费者只要有一个慢处理，整条队列
就会被拖死**——vnpy 论坛有完全同款的 ["queue 被 hang 住"](https://www.vnpy.com/forum/topic/31321-event-enginede-queuedui-lie-bei-hangzhu-liao)
与 [stop 卡死](https://www.vnpy.com/forum/post/70349) 讨论。结论一致：
**事件循环里只做快活，慢活全部异步化**。

### 1. 前端首屏与合约列表（第 1 优先，~1 小时，立竿见影）

拥塞的唯一放大器就是"打开页面 = 查 866 个合约"：

- `app.js init()` 不再无条件 `loadInstruments()`：初始只显示**自选 + 当前合约**；
  合约列表按需加载——点交易所标签（≤200 个/所）、输搜索词（keyword 路径实测 1~2 秒）才请求；
- 确需全量浏览时做**虚拟滚动**（只渲染可见行，866 行毫无压力），可选零依赖方案：
  [hyperlist](https://github.com/tbranyen/hyperlist)、
  [clauderic/virtualized-list](https://github.com/clauderic/virtualized-list)、
  [hcg-virtual-scroll](https://github.com/html-code-generator/hcg-virtual-scroll)，
  或最简单的**分页**（每页 100 个 + 上一页/下一页）；
- 目录请求失败后自动重试（指数退避，挂到现有 15 秒 `loadStatus` 周期上即可）。

### 2. 后端目录查询协程化 + singleflight + 结果写回（第 2 优先，~1 天）

**关键升级：用 TqSdk 官方协程机制实现"让出"，而不是自己发明分片。**

TqSdk 2.6.1+ 支持[在同一个 api 上挂协程任务](https://doc.shinnytech.com/tqsdk/latest/advanced/multi_strategy.html)：

```python
api.create_task(catalog_worker(api, manager))   # 挂到 api 的更新循环上

async def catalog_worker(api, manager):
    while True:
        batch = manager.next_pending_batch(50)      # 取一批待查合约
        if batch is None:
            await asyncio.sleep(1); continue
        frame = TqSymbolDataFrame(api, batch, None)
        try:
            await _wait_task_async(api, frame, 20)  # 官方 await 写法
            manager.write_batch(frame)              # ★ 完成就写缓存，与 HTTP 等待方解耦
        except Exception:
            manager.cooldown(batch)
```

- 主循环 `wait_update()` 驱动一切：每批查询等待期间，K 线/订阅/行情推送**照常处理**；
- **结果写回与 HTTP 等待方解耦**：查询完成就写 `_info_cache`，HTTP 请求只读缓存 +
  返回"目录加载进度"——彻底修掉"120 秒超时把已完成的 18 批结果全部扔掉"的死穴；
- `/api/v1/instruments` 改成：缓存有多少返回多少 + `progress` 字段
  （`{"items": [...已就绪的...], "progress": {"done": 400, "total": 866}}`），
  前端显示进度条而不是报错；
- **singleflight 去重**：同一个 key 的并发查询只执行一次，其余等结果——防止
  页面轮询 + 多客户端把同一批查询排队多次。直接可用现成库：
  [roman-postnov/coalescer](https://github.com/roman-postnov/coalescer)（asyncio+线程双支持）、
  [eugeneliukindev/oneflight](https://github.com/eugeneliukindev/oneflight)（零依赖）、
  [PyPI singleflight](https://pypi.org/project/singleflight/)；模式出处是 Go 的
  `golang.org/x/sync/singleflight`（防止缓存击穿的"请求合并"）；
- 后端**启动即预热**：lifespan 里 `create_task` 预热目录，用户还没打开页面它就在后台慢慢查了。

> 备选快赢：TqSdk 自带 `TqApi(auth=..., web_gui=True)` 可直接生成网页看盘
> （[官方仓库](https://github.com/shinnytech/tqsdk-python)），可作为自研 UI 完成前的过渡。

### 3. 队列与线程池治理（防活锁，~半天）

- **超时即取消**：future 超时后给命令打"已放弃"标记，`_process_commands` 执行前跳过
  已放弃命令——不再"执行了也白执行"地堆队列；
- **线程池**：FastAPI sync 端点共享 anyio 默认 **40 线程**上限（[AnyIO 文档](https://anyio.readthedocs.io/en/stable/threads.html)、
  [Starlette Thread Pool](https://starlette.dev/threadpool/)、[fastapi#5759](https://github.com/fastapi/fastapi/issues/5759)）。
  两手修：① lifespan 里 `anyio.to_current_thread_limiter().total_tokens = 100` 适当调大；
  ② kline/decision/instruments 改 `async def` + 用一个 `asyncio.Semaphore` 保护
  "提交命令 + 等待"段（等待期不占线程），从机制上消除线程池耗尽；
- **错误语义**：`TqClientError` 统一映射 503 + JSON；决策端点区分
  "目录未就绪（503, retry_after）"与"合约不存在（422）"。

### 4. 前端图表状态与竞态防护（~2 小时）

- **请求竞态**：`loadKline`/`loadDecision` 加自增序号，响应回来时序号不对就丢弃；
  同时切合约/周期时用 `AbortController` 主动取消旧请求——`fetchJSON` 本来就支持
  传 `options.signal`，只是 `loadKline` 没用上；
- **加载态**：切换期间图表加半透明"加载中"遮罩，绝不显示旧数据冒充新合约；
- **提示自愈**：成功时清除"K线加载失败"文字（现在的 bug：图已经画好了提示还挂着）；
- **ECharts 大数据**：参照[官方大数据实践](https://echarts.apache.org/)给系列加
  `sampling: 'lttb'`、`large: true`，K 线量上去后用 `progressive` 分片渲染；
  官方有 [Large Scale Candlestick 示例](https://echarts.apache.org/examples/en/editor.html?c=large-scale-candlestick)可对齐参数；
- 若日后想换更专业的 K 线组件：[KLineChart](https://github.com/klinecharts/KLineChart)
  零依赖、内置常用指标与画线工具，是天勤/QUANTAXIS 等社区常用的选择
  （参考 [quant-trade](https://github.com/Riki-WangJJ/quant-trade) 的 FastAPI+Vue 行情架构）。

### 5. 运维与安全（~1 小时）

- 后端加**文件日志**（轮转）替代 stdout：排查两次"进程无征兆消失"必须先有持久日志；
- Electron 侧已有 spawn/清理逻辑，可加 30 秒心跳探测（`isServerUp` 已存在），挂了自动拉起；
- **密码治理**：`git rm --cached config.json` + 天勤改密；历史提交里的密码用
  `git filter-repo` 清理（仅本地仓库，成本低）。

### 6. 小问题清单（顺手修）

- `MarketQuote` 补 `pre_open_interest` 字段，恢复量仓评分与"日增仓"显示；
- 最新价虚线 label 防右缘裁剪；
- vnpy_tqsdk 的教训也记一笔：它的 `tqsdk_datafeed.py` 把 `api.close()` 放在
  try/except 之外（不在 finally），异常路径会泄漏连接——我们的 `TqClient._run` 已用
  finally 关闭，保持住。

## 六、修复后的验收清单

1. 重启后端 → 直接打开页面：K 线 ≤10 秒显示，全程不出现 500；
2. 打开页面的同时 `curl /api/v1/status` 始终 <1 秒响应（线程池不再被占满）；
3. 切合约/切周期：图表 ≤3 秒切换，或显示明确"加载中"，绝不残留旧合约数据；
4. 目录预热期间：合约列表显示进度，搜索/切换其他功能不受影响；
5. 拥塞场景复测：脚本同时打 10 个 kline 请求，其余接口不受影响；
6. 决策面板不再出现"合约不存在"误报；
7. 长跑 1 小时页面常开，后端内存/线程数稳定，进程不消失。
