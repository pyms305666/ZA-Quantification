## 本次已完成

### Android 与行情链路

1. 锁屏持续行情：`BackendService` 以前台服务运行，并配合 `PARTIAL_WAKE_LOCK` 与电池优化
   白名单引导，锁屏后本地后端仍可响应、行情继续接收。
2. 冷启动订阅：目录尚在加载时，订阅会先写入客户端队列，不再等待目录造成 10 秒超时；目录或
   WebSocket 就绪后自动发出 `subscribe_quote`。
3. 目录状态：区分“可搜索”与“已完整”，增量目录未包含某合约时不再误判为不存在；完整目录中
   未命中才严格拒绝。
4. 断线恢复：行情 WebSocket 重连后自动重放报价订阅和 K 线图表状态。
5. 已有修复继续有效：手机 WS 广播、中文名称搜索、合约列表分页、K 线增量渲染与决策接口。

核心共享文件的桌面/手机镜像已通过 `tools/check_core_drift.py --strict` 校验。修改 `tq/`、
`tqdiff/`、`market/` 或 `services.py` 时，必须同步 `mobile-app/app/src/main/python/` 中的镜像。

## 网页版边界

网页版不是独立的云产品：`static/` 是 Web UI，`api/`、`tq/`、`tqdiff/` 是本地 FastAPI 后端，
通过 `main.py` 或 `launcher.py` 启动。Electron 只是同一 Web UI 的桌面壳。

因此本次不需要修改 Web 前端页面。若网页服务运行的代码包含 `5a568d1` 及其前置修复，只需重启
后端进程即可获得目录加载和重连订阅改进。

仓库的 `origin/main` 目前是无共同历史的空初始化分支（`bcafc41 Initial commit`），不是可直接
部署的生产分支；默认远端 HEAD 指向 `origin/master`。在未确认实际服务器的代码来源前，不能把
`mobile-app` 直接合并或强推到 `main`，否则会把 Android 工程和无关历史带入错误分支。

## 下次接手的操作顺序

1. 确认线上网页服务实际运行的位置、启动命令和所跟踪分支。当前仓库没有 Docker、Vercel、Render、
   Fly.io 或 CI/CD 配置，不能从仓库自动推断或自动部署。
2. 若线上服务基于本仓库旧代码，创建一个以实际生产基线为父提交的 Web 发布分支，仅迁移共享后端
   修复，并在服务器重启前执行以下验证：

   ```powershell
   python -m unittest discover -s tests
   python tools/check_core_drift.py --strict
   cd electron
   npm test
   ```

3. 服务器上更新代码与 Python 依赖后，重启 `main.py`/`launcher.py` 对应的进程；用
   `/api/v1/status` 检查 `connected`、`catalog_ready`、`catalog_complete`、`catalog_loading`，
   再验证 `/ws/market` 的报价推送与断网恢复。
4. 下一个 Android 发布前，使用 JDK 17、SDK 34 在 `mobile-app/` 执行
   `./gradlew.bat --no-daemon assembleDebug`，安装到真机，并复测锁屏、冷启动、断网恢复、K 线与
   中文搜索。构建约束详见 `mobile-app/README.md`。

## 已知维护项

- 桌面 Python 与 Android Chaquopy Python 存在双份核心代码，需要严格漂移检查。
- 凭据仍可能以本机明文 JSON 保存；优先用环境变量，并避免把密码提交到仓库。
- 完整合约目录下载没有断点续传；内置精简目录和缓存是可用性兜底，不等于完整目录。
- Android 需要建立 release keystore、签名、验签与升级策略。
- 需要确定网页实际部署位置后，建立受控发布分支、部署脚本与健康检查，避免以空的 `main` 分支作为
  部署依据。
