## ⚠️ 发现的问题（未改代码，仅记录）

### 问题 A：启动时自选批量订阅未生效，自选价格显示 "--"
- 现象：13:37:47 App 启动完成（APP_INIT），13:38:10 后端 `connected=true, catalog_ready=true` 但
  `subscribed=[]`；13:40:44 截图自选 4 行价格全部 "--"——**持续 3 分钟以上**，直到外部（REST）订阅才恢复。
- 定位线索：`static/app.js` `connectWS().onopen` 会一次性订阅全部自选（app.js:280 起的实现），
  但该次订阅在后端行情链路尚未就绪时发出后**没有重试**；后端订阅表始终为空。
  疑似与后端 hub 启动时序竞争（与此前"自选不显示价格"投诉同源，之前的修复只解决了
  "有数据后的回填渲染"，没解决"首次订阅丢失后不再补订"）。
- 复现补充（13:52 完整复现）：冷启动（新进程 14188）后连续 90 秒轮询，`connected=True` 但
  `subscribed=[]`、`quote_recv_total=0`，自选 4 行价格全部 "--"（截图 `phone_screen_app_fg.png`）。
- 根因链条（已锁定）：
  1. `tq/subscriber.py::SubscriptionManager.subscribe` 开头：行情未连接时整批直接返回
     `failed: 天勤未连接`，不登记任何符号；
  2. `static/app.js::connectWS().onopen`：页面加载即一次性发送自选订阅——此时后端天勤链路
     尚未连上（UI 显示"连接中"），订阅必然落在失败窗口里；
  3. app.js 不检查订阅返回、失败后无任何重试；轮询接口（kline/decision/status）也不补偿订阅。
  → 结果：除非用户手动操作，订阅永远是空的，行情永远不来。
- 恢复路径验证（13:53）：点击自选里的**非当前**合约（au2612）→ `switchSymbol` 重发"当前+全部自选"
  订阅 → 3 个可交易合约全部补订成功、行情流入，自选价格全部显示
  （rb2610 3,048.00 +0.40% / au2612 933.36 / lh2611 11,285.00，截图 `phone_screen_prices_ok.png`）；
  过期的 m2609 正确保持 "--"。
  注意：点击**恰好等于当前默认合约**（rb2610）时 `switchSymbol` 直接 `return`，不会补订——
  这正是默认合约在首屏一直 "--" 的原因。
- 修复方向（待用户确认后再动代码）：后端连接建立后重放失败的自选订阅（订阅管理器把
  "未连接时的失败"挂起为 pending，连接就绪后自动补订）；或前端订阅失败时指数退避重试。
- 顺带发现（轻微）：行情页顶部快捷卡片（黄金2612/豆粕2609）在自选已有价格时仍显示 "--"，
  卡片与自选行数据源不一致，不影响自选行本身。

### 问题 D：合约浏览双重截断——"目录只看得到一部分"
- 用户反馈：行情界面从来没看到过完整目录（目录实际 578 条期货）。
- 两层截断叠加：
  1. 后端 `mobile_api.py` instruments 路由硬编码 `limit=200`（无关键字浏览最多返回代码序前 200 条）；
  2. 前端 `renderSearch` 只渲染 `slice(0, 50)`，无分页/滚动加载——搜索结果也只画前 50 条。
- 实测：`GET /api/v1/instruments`（无关键字）返回恰 200 条，从 DCE.a2611 起。
- **修复方案（用户已定）：limit 放开**，前端补滚动加载。

### 问题 E：中文关键字搜索失效——搜"棕榈"0 条（两端同病）
- 实测（手机端，交易时段）：`keyword=棕榈` → 0 条；`keyword=p26` → 14 条
  （DCE.p2610/2611/2612 棕榈均在目录中，名称字段"棕榈2610"正常返回）；`keyword=p` → 95 条。
- 根因：`tq/instruments.py::list()` 的候选预过滤只按**代码**匹配
  （`code_keyword not in symbol.lower() → continue`），中文名关键字在预过滤即被全部丢弃、
  提前 `return []`；后面写好的名称匹配（`haystack = symbol + instrument_id + name`）永远执行不到。
- 影响范围：桌面端同一实现（tq 统一后逐字节一致），中文搜索同样失效，非手机独有。
- 修复方向：预过滤阶段对非 ASCII 关键字（或所有关键字）不能只看代码——需先拿到名称索引再过滤
  （名称已在精简索引 pickle 中，无需逐合约网络查询）。

### 问题 B：锁屏后 App 被系统冻结，后端停止服务
- 现象：13:43 手机锁屏后（App 退到后台），`pidof` 仍返回 8808，但 HTTP 12s 无响应（HTTP 000），
  WebSocket keepalive ping 超时断连（latency_probe 于 13:43 左右 ConnectionClosedError）。
- 判断：vivo 后台冻结策略把 App 进程整体冻结，Python 后端随之中止服务。
  进程"活着"但不干活，`pidof` 检查会误判为正常。
- 影响：锁屏期间 App 完全无行情；解锁恢复后的重连/重订阅行为待验证。
- 缓解方向（待用户决策后再动）：引导用户把 App 加入电池白名单/自启动管理，
  或申请前台服务（foreground service）保活；验证脚本需用"HTTP 探活"而非"进程存在"判定冻结。

### 问题 C（最严重）：手机端行情 WebSocket 广播从未生效——UI 价格只靠"订阅时快照+REST 轮询"
- 现象：交易时段行情持续流入（`quote_recv_total` 0→1976），但外部 WS 客户端监听 30 秒
  只收到 `hello` + `subscribed`，**0 条 quote 广播**；5 分钟延迟采样 0 样本。
- 根因（三处断点，APK 内源码已逐一核对）：
  1. `services.py::build_services`：`client.set_callbacks(on_quote_change=services.on_quote_change, …)`
     ——行情回调挂在 **Services** 对象上，而**不是** MobileHub 的；
  2. `services.py::Services.on_quote_change`：只有 `services.loop` 非 None 才入队——
     手机端 lifespan（`mobile_api.py::on_startup`）只设置了 `hub.loop`，**从未设置 `services.loop`**；
  3. `mobile_api.py::MobileHub.on_quote_change → _enqueue → hub.queue → _broadcast_loop`——
     整条链路是设计好的，但 `MobileHub.on_quote_change` **没有任何地方注册**，属死代码。
  → 桌面版（api/http.py lifespan 设置 services.loop 并启动 `_broadcast_loop(services)`）两端不对称，
  手机版广播管道从未接通。
- 对用户体验的实际影响（与历史投诉吻合）：
  - 自选/报价头价格只在新订阅瞬间由内联 `quote_snapshot` 刷新一次；重连时全部 "skipped"
    （快照只对本次新订阅的合约发），**价格随后冻结**；
  - K 线图实际靠 20 秒 REST 轮询在动（此前已实测 REST 链路正常），盘中"感觉不实时"由此而来；
  - `quote_snapshot` 与广播 `quote` 消息里，快照路径无 `ts` 字段，前端延迟统计也无从谈起。
- 修复方向（待确认后动代码）：lifespan 里 `client.set_callbacks(on_quote_change=hub.on_quote_change)`
  （或在 hub.on_startup 中同步设置 `services.loop` 并复用 services 广播队列），二者取其一即可接通。
