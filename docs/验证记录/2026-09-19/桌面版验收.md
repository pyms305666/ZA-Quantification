## 二、问题清单与解决方案

### 问题 1：目录下载速度极慢（~20KB/s），且同 IP 并发下载互相饿死

- **现象**：TTL 到期触发的重下载在 gzip 快路径上只有 ~20KB/s（昨夜手机端实测 ~115KB/s）；
  期间 concurrent 运行的续传探针（identity 长流）运行时，桌面 gzip 下载 20 秒纹丝不动
  （0MB），停掉探针后立即恢复推进——服务器按 IP 维度限速，长连接大流量会持续挤占
  同 IP 其他连接的额度。
- **影响**：目录重下载期间（约 7 分钟~更久）搜索不可用（内置表兜底可搜 156 个主流合约，
  但"棕榈"等命中 0）。功能不中断，只是慢。
- **解决方案**（按优先级）：
  1. **短期·运维约定**：不要在目录下载时并行跑 `catalog_resume_probe.py` 等大流量工具
     （已写入探针脚本 docstring 提示——待补）；
  2. **中期·代码**：目录重下载提前到 TTL 到期前的空闲时段（如剩余寿命 <24h 且已连接
     时后台静默刷新），用户几乎永远不会再撞上"当天等目录"；
  3. **可选**：`If-Range` 续传已经兜底，无需再加速协议本身。

### 问题 2：`dist/` 里的 AB 协程版 exe 是旧代码

- **现象**：`dist/ZA量化-AB协程版.exe` 与 `sha256.txt` 中对应条目停留在旧版本
  （交接文件已标注"未重打"）。用户若误用会拿到没有近期修复的版本。
- **解决方案**：二选一——(a) 用 AB 路线分支重打包一次并刷新 sha256；
  (b)（推荐）从 `dist/` 与 `sha256.txt` 移除该产物，README 已只主推 C 直连版，
  双路线早已裁定收敛于 C。

### 问题 3：Windows 安装器未随 v1.1.3 重编

- **现象**：本机无 Inno Setup（ISCC），`installer/c.iss` 已更新到 1.1.3 但未编译出
  `ZAQuant-V1.1.3-C-Direct-Setup.exe`；`sha256.txt` 中还是 V1.1.1 安装器条目。
- **影响**：只想用安装器的桌面新用户暂时没有 v1.1.3 安装包（绿色版 exe 可用）。
- **解决方案**：在装有 Inno Setup 6 的机器上执行 `ISCC installer/c.iss`（1 分钟），
  产物入 `dist/` 并刷新 `sha256.txt`；或本机安装 Inno Setup 6 后同样操作。

### 问题 4（真 bug，已修复并验证）：目录缓存被内置表永久钉死

- **现象**：TTL 到期重下载完成后，`catalog_complete=true` 但 `/api/v1/instruments`
  仍返回内置表 156 条、"棕榈"搜索 0 条——直到重启或手动 `?refresh=true`。
- **根因**：`InstrumentManager.futures()` 首查后永久缓存（refresh=False）；而
  `/api/v1/status` 每次轮询都调它——冷启动时首查必然发生在目录未就绪阶段，
  内置 156 条从此钉死。**两端共有**（手机端同样代码，近期会话恰好没踩中：
  目录缓存命中时首查即是完整表）。对全新安装的手机，目录下载期间搜索/列表
  会一直空到重启——交接文件 §6.1"搜索不可用"的又一个根因。
- **修复**：缓存记录建立时的目录完整性，目录由内置转完整后的首次访问自动重查
  一次（常态零开销）。`tq/instruments.py`（两端镜像），+2 个回归单测
  （转完整自动重查 / 未完整不重复查询），全套 **81/81**、漂移 0。
- **端到端验证**：清缓存冷启动 exe（无 pickle 索引），`futures_count` 无需人工
  刷新自动 156 → 581（见 `桌面自愈验证.txt`）；棕榈搜索恢复 12 条。
- **发布物**：两端产物已用修复版重打，GitHub Release 附件已替换并更新校验值。
