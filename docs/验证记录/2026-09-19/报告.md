## 二、断点续传专项（本次核心）

### 2.1 真机（真实服务器 + 真实断网）

- 飞行模式切断下载中的目录 → logcat 实证双路径降级：
  ```
  [catalog] gzip fast path failed: …NameResolutionError…; fall back to identity resume
  [catalog] identity path: part_offset=0 etag=none
  ```
  （`logcat_catalog_excerpt.txt`；完整日志 `phone_logcat_full.txt`）
- 恢复网络后 30 秒重试窗口内自动重启下载并推进（0→4MB，后因夜间限速缓慢，最终
  在 09-20 前完成——09-20 启动时索引已就绪即为完成证据）。
- **边界说明**：真机只能确定性地证明"降级发生"；"206 断点续传收尾"由桌面探针
  （同一份逐字节镜像代码 + 真实服务器）覆盖，见 §2.2。原因：gzip 快路径与续传路径
  在同一次调用内先后执行，纯断网会让两条路径一起失败（详见 `tqdiff/auth.py` 注释）。

### 2.2 桌面探针 + 真实服务器续传契约（真服务器验证）

- 工具：`tools/catalog_resume_probe.py`——预置 `.part`（Range 取前 4096 字节 + ETag），
  调用与手机**逐字节相同**的 `tqdiff/auth.py`，验证 206 追加→解析→清理全链路。
- 探针实测（09-20）：正确进入续传路径（log 行
  `[catalog] identity path: part_offset=4096 etag=stored`），`.part` 持续增长。
  **重要发现：服务器对 identity 未压缩流限速约 36KB/s（gzip 快路径约 500KB/s，差
  ~14 倍），identity 全量 354MB 需近 3 小时**——真实弱网下 identity 中断必然频发，
  印证"gzip 优先 + 续传兜底"的混合设计必要性。探针完整 PASS 行后台跑完后见
  `probe_206.txt` 尾部。
- **续传契约硬证据**（`resume_contract_curl.txt`）：用探针同款 ETag 发
  `Range: bytes=4096-` + `If-Range` + `Accept-Encoding: identity`，
  真实服务器返回 **`206 Partial Content`**——续传请求被服务器原样接受。

### 2.3 单元测试（12 个，全部通过）

`tests/test_tqdiff.py::DownloadSymbolFileTests`：gzip 快路径、降级触发、206 续传、
ETag 变化重置、416 两种分支、解析失败清状态、断流保留状态后续传、明文/gzip 解析
一致性等。全套 79/79 通过。

### 2.4 测试期间发现并修复的缺陷

1. **`urllib3.ProtocolError` 不是 OSError 子类**：连接中途重置会绕过降级逻辑
   （gzip 与旧版代码同病）。修复：捕获集补 `urllib3.exceptions.HTTPError`。
2. **ETag 落盘时机**：原实现收完流才写 ETag——identity 全量 354MB/弱网约 12 分钟，
   首次中断即丢续传凭据。修复：ETag 在收到响应头后、收流前落盘。
   各配一个针对性单测（`test_midstream_reset_falls_back_to_identity`、
   `test_identity_break_keeps_state_then_resumes`）。
